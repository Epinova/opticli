❯opticli

A command-line tool for the content in your Optimizely CMS 12 or CMS 13 site. Look up pages and blocks, trace them to the code that renders them, and change them through the CMS API, from your terminal or through your coding agent.

What it's for

  • Answer content questions without SQL

    No more hand-written queries against tblContent. Items come back with every property decoded, including ContentAreas, local blocks, links and rich text. Reads go straight to the database, so the site doesn't need to be running.

    opticli get 123 --fields MainContentArea

  • Go from content to code

    See the C# class for a content type, the source line of each property and the Razor views, plus which ContentAreas accept it according to [AllowedTypes].

    opticli type TeaserBlock

  • Know what a change will affect

    Find every page and block that references an item, through nested blocks all the way up to pages. You can also resolve a URL to content, or list the unpublished drafts.

    opticli where-used 456 --pages

  • Change content through the CMS API

    Writes go through IContentRepository inside your running site, so validation, versioning, events and caches all work. Changes are saved as drafts unless you publish, and every write command takes --dry-run.

    opticli set 123 Heading="New title" --dry-run

  • See changes in the site you're debugging

    With ide on, the site you start from Rider or Visual Studio loads the agent from its own build, so opticli writes through that process and a reload shows the change, without a restart. Nothing to set per run, HTTPS with the development certificate works, and the debugger, hot reload and breakpoints stay as they are.

    opticli ide on

  • CMS 12 and CMS 13

    The same commands on both, for fresh CMS 13 installs and databases upgraded from CMS 12. Reads follow the database's schema, and serve picks the site agent built for your site's CMS version. On CMS 13, sites are applications, and the template's LocalDB connection string works as it is on Windows.

    opticli doctor

  • Visual Builder pages

    get shows an experience as its sections, rows, columns and elements, with display templates and settings. composition adds, moves, changes and removes them, or writes back the JSON get printed. Content variations and blueprints work too.

    opticli composition 123 add element --in Left --type TextElement Heading=Hi

  • Deletes that check first, and come back

    delete only moves content to the recycle bin, and stops while other pages or blocks still reference it, listing where. trash shows what's in the bin and where it came from, and restore puts it back there.

    opticli delete 456 --dry-run

  • Take content offline, and back

    unpublish takes a page offline as the edit UI's expiry does and names the version that was live, so publishing it puts the page back. discard removes a draft that was never published.

    opticli unpublish 123

  • Approvals and scheduled publishing

    Content with an approval sequence is never published past its reviewers: --request-approval sends it for review instead. --publish-at leaves the publish to the CMS's scheduled job.

    opticli publish 123 --request-approval

  • Upload files as media

    A file becomes a media item of the type the site registers for its extension, in a page's own folder or any other. The output says where the site stored it.

    opticli upload price-list.pdf --for 123

  • Read and change access rights

    See who may read and edit an item and where that is inherited from. Changes apply to that one item and never leave the site without an administering role.

    opticli access 123 --revoke Everyone

  • Plans you can run again

    With "guidNamespace" every item a plan creates gets the same GUID in every database. --update-existing then updates what is there, restores it from the recycle bin, and leaves finished steps alone. export writes existing content of any database as such a plan.

    opticli apply plan.json --update-existing

  • Rich text from files

    A plan value of "@body.html" is that file's text, so long rich text stays in reviewable files next to the plan instead of inside its JSON. In it, href="$id" links to content the plan creates, saved as its permanent link.

    "MainBody": "@body.html"

  • Dry runs that reach every step

    Steps on content the plan hasn't created yet run against stand-ins, so validators, required properties and [AllowedTypes] are checked before anything is written.

    opticli apply plan.json --publish --dry-run

  • The page settings editors use

    Shortcuts and external links, simple addresses, categories, child sort order and sort index, and publish dates. get shows them, and diffs name what changed.

    opticli set 123 SimpleAddress=campaign

  • A production copy, on localhost

    After restoring a production database, one command makes your local host each site's primary host and moves SiteUrl with it, so links and canonical URLs stay local. The production hosts stay too. Save the mapping once and run it again after every restore. users add gives you a local admin login, its password in a file only you can read.

    opticli sites primary --from-config

  • Production's content, without a bacpac

    sync pull brings what editors did in production into your local database: new, changed and moved content, matched by GUID and written through your local site. It only reads production, keeps your own local changes, lists conflicts instead of overwriting them, and remembers what it synced, so the next pull is quick.

    opticli sync pull --from prod --all --dry-run

  • Changes for production: the agent seals, you run

    A coding agent can prepare content for production but never write it. sync push seals what changed locally; you run the command it prints in your own terminal, see what it does, type the database's name and a write login that is never saved. It runs only if the plan, the build and production are as sealed.

    opticli sync push --to prod /en/campaign/

  • Scheduled jobs, without surprises

    See every job's schedule, last run and log, and where its code lives. Run one and wait for its result, stop it, or change when it runs. serve keeps a restored database's overdue jobs from all running at once, and jobs that delete for good need an explicit flag.

    opticli jobs run "Content import"

  • Clean up what removed code left behind

    types --orphaned finds content types whose code is gone, and type shows leftover properties with their stored values. types prune removes what can go through the CMS, never content, records every removal first, and needs a flag before it deletes stored values.

    opticli types prune --dry-run

  • What happened to it?

    history reads the change log for one item: moves, deletes, restores and publishes, with who and when.

    opticli history 123

  • Nothing to add to your solution

    serve starts your existing build with a small agent injected at startup, through a .NET startup hook and a hosting startup. Your site's code and config stay as they are. ide on only adds a block to your own .csproj.user, which git ignores.

    opticli serve

  • Claude for editors, on any environmentPreview

    The OptiCli.Mcp package adds an MCP server to the site itself, production included. Editors connect Claude, sign in with the site's own login, and Claude works as them, with their access rights.

    dotnet add package OptiCli.Mcp --prerelease

  • Built for coding agents

    Piped output is compact JSON. Every item has a ref you can pass to the next command, and errors come with a code and a hint. A Claude Code skill tells the agent when to use opticli and how to use it safely.

    opticli skill install

How it works

Readsopticli── fixed read-only SQL ─▶CMS database
Writesopticli── 127.0.0.1 + token ─▶agent in your running site── IContentRepository ─▶CMS database

Safety

  • Which database does it use?Your local one by default: opticli reads the connection string from the site's Development config. To use a remote database you have to choose it explicitly, and every response then carries a warning.
  • Can a read change anything?No. Reads use fixed queries. opticli sql accepts a single SELECT against the site's own database and runs it in a transaction that is rolled back.
  • Can it publish or delete by accident?Changes are saved as drafts by the user opticli. Publishing needs --publish, and delete only moves content to the recycle bin, and not while other content still references it.
  • Can it write to production?Not on its own. A database with the role prod is only ever read: every response carries a warning, and serve and every write, dry runs included, are refused. The one way in is a sealed apply that you run in your own terminal, with a write login you type and opticli never saves; an agent can prepare and seal it, not run it.
  • Can starting it change a shared database?Against a remote development database, the scheduler, schema updates, content type sync and store remapping are off, and serve won't start a build with EF Core migrations the database lacks. The CMS still registers the build's scheduled jobs and add-on content roots there, and the site's own startup code still runs, so use a login without DDL rights where your add-ons allow it.
  • What if my branch isn't what's deployed?opticli compares the build with the shared database: content types, properties, migrations. While they differ, writes stop until you confirm with --accept-drift, and it says which side is ahead. Reads keep working.
  • What can the MCP server do to a production site?Only what the signed-in editor may do: every read and save is checked against their access rights, and content they can't read looks the same as content that doesn't exist. Changes are drafts, without script. Publishing and deleting are off until the site turns them on, and approval sequences always apply. Only Claude, or an app on the editor's own machine, can be connected, and editors can see and revoke their connections.
  • Can anyone else reach the site agent?It answers only to requests from this machine, only in Development, and only with the token of that run, which sits in a file only you can read. Requests that came through a proxy or tunnel are refused.
  • Does the site I debug start differently?No. With ide on, the agent doesn't pin the database or touch the scheduler, and it never stops the site from starting: against another database, or outside Development, it just stays off for that run and says why.

Get started

You need the .NET 8 SDK or newer. Install opticli from nuget.org as a global tool, then run it from anywhere inside a CMS 12 or CMS 13 site's repository.

# install, or update to the latest version
dotnet tool install -g OptiCli
dotnet tool update -g OptiCli

# then, in your site's repository
opticli doctor                          # what it found: project, database, content types
opticli resolve https://example.com/en/about/
opticli skill install                   # teach Claude Code to use it

For editors: an MCP serverPreview

opticli itself is for developers on their own machine. OptiCli.Mcp is a NuGet package you install in the site, so editors can connect Claude (claude.ai, Claude Desktop, Claude Code) to it in any environment. Editors sign in with the site's own login, Entra ID or ASP.NET Identity, and approve the connection. Claude then reads and changes content as that editor, with their access rights, through the same operations as the CLI's site agent: drafts by default, dry runs, validation and approval sequences. Claude also sees the images in the media library.

It is a preview, published as a prerelease, and not yet recommended for production: the options and tools may still change. It supports CMS 12 (12.12.1 and CMS UI 12.16.1 or newer), not CMS 13. claude.ai and Claude Desktop need the site to be reachable from the internet. See the README for every option.

# in the site's project
dotnet add package OptiCli.Mcp --prerelease

# Startup.cs
services.AddOptiCliMcp();               # after the site's own login setup
endpoints.MapOptiCliMcp();              # after MapContent() and the site's own endpoints

# editors then connect Claude to
https://your-site.example/episerver/opticli/mcp
